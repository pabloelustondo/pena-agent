# PENA-Agent Development Instructions

## Methodology: SDLC 2026 (Overlapping, Knowledge-Centric)

This project follows a spec-driven, knowledge-centric software development lifecycle. Steps can overlap (like RUP), but all due diligences must be completed.

### Development Loop

```
Context → Intent → Benchmark → Specs → Planning → Vibe/POC → AI-Assisted Build → Runtime → Observability → Feedback → Learning ↻ Context
```

**Key principle:** Steps are not strictly sequential. Early phases can overlap with later phases, but each step must be completed before code ships to production.

---

## Due Diligences by Phase

### Context Phase
- [ ] Problem domain is understood
- [ ] Constraints are documented (technical, scope, organizational)
- [ ] Assumptions are explicit and tested
- [ ] Tools and dependencies are evaluated
- [ ] Team knowledge and roles are clear
- [ ] Folder structure reflects knowledge-centric architecture

### Intent Phase
- [ ] Project vision is clear and written
- [ ] Goals are specific and measurable
- [ ] User/user-story is explicit
- [ ] Success criteria are defined
- [ ] Scope boundaries are documented

### Benchmark Phase
- [ ] Success metrics are quantified
- [ ] Reference behavior is described
- [ ] Acceptance criteria are explicit
- [ ] Comparable systems are analyzed
- [ ] Performance targets are set

### Specs Phase
- [ ] Requirements are written as specs
- [ ] APIs/interfaces are defined
- [ ] Behavior is documented with examples
- [ ] Edge cases are considered
- [ ] Specs connect back to benchmarks

### Build Phase
- [ ] Implementation follows specs
- [ ] Code is connected to benchmark targets
- [ ] Observability is built in (not added later)
- [ ] Tests validate against spec
- [ ] Nothing ships without observability

### Observability & Learning Phase
- [ ] Metrics are collected and visible
- [ ] Behavior is traceable
- [ ] Failures are logged with context
- [ ] Feedback is systematized
- [ ] Learnings feed back to Context

---

## Knowledge-First Architecture

This repository treats the following as first-class artifacts:

1. **Context** — Domain, assumptions, constraints, history
2. **Specs** — Requirements, APIs, behavior definitions
3. **Benchmarks** — Success criteria, targets, examples
4. **Observability** — Metrics, traces, dashboards
5. **Learning** — Decisions, retrospectives, tool evaluations
6. **Prompts & Instructions** — Agent definitions, system prompts
7. **Code** — Runtime implementation

Code without specs, specs without benchmarks, and implementations without observability are incomplete.

---

## Guidelines

1. **Start with a spec, not a branch.** Before coding, write or update a spec.
2. **Observe everything.** Every feature should have explicit observability (logs, metrics, traces).
3. **Connect decisions to learning.** Every architectural or process decision should be documented with rationale.
4. **Benchmark before building.** Every feature should have an explicit benchmark before implementation.
5. **Feedback loops matter.** Observability data must drive improvements in specs, benchmarks, or methodology.
